## 2. Functional bugs (Phase 2 — exploratory + backend verification)

All three P1s below were found by agent-as-user walks and then **independently reproduced deterministically** against the QA backend (raw API + DB inspection), with the root cause traced to a specific line. All three are **auto-filed**.

### FB-1 — Attendance cannot be saved for any recurring class · **P1** · FILED PAD-64
- **Where:** Calendar → open a class → "Mark attendance" → mark Present → Confirm.
- **Symptom (exploratory):** red toast "Failed to save attendance"; `POST /api/app/class_instance/presences/confirm → 404` (Flask default 404 page); no attendance recorded on reopen.
- **Deterministic repro (raw API, this run):**
  - Materialized `LessonInstance` (seeded "E2E Academy Class", `model:"LessonInstance"`) → **HTTP 200**, saves fine.
  - Recurring `Lesson` occurrence (seeded "E2E Recurring Class", `model:"Lesson"`, `originalId:2`) → **HTTP 404**.
- **Root cause:** `confirm_presences_service` (`levelup_backend/padel_app/services/lesson_service.py:501`) branches on `if 'parentClassId' in class_instance_data.keys()`. The calendar API **always** includes `parentClassId` in every event object (value `null` for non-instances), so the condition is **always true** — even for `model:"Lesson"` recurring events. It then calls `LessonInstance.query.get_or_404(originalId)` where `originalId` is a **Lesson** id → no such LessonInstance → `get_or_404` → 404. The intended `else` branch (materialize from the Lesson) never runs.
- **Fix direction:** branch on the event `model` (or on a **truthy** `parentClassId`), not on mere key presence.
- **Coverage gap:** the passing `attendance.spec.ts` US-20 only *views* the roster; the save/confirm path has **no** regression coverage — which is why this shipped.
- **Impact:** a coach cannot record attendance for any recurring class occurrence (until some other edit materializes it). Core coaching flow, deterministically broken. → **P1.**

### FB-2 — Deleting an edited recurring occurrence resurrects it with pre-edit values · **P1** · FILED PAD-65
- **Where:** Calendar → edit one occurrence of a recurring class (title/time) → delete it (confirm) → navigate weeks / reload.
- **Symptom (exploratory):** after `remove_class → 200 {"status":"single_removed"}` and the class disappearing, it **reappeared** on a full reload (confirmed server-side via `GET /api/app/calendar`) with its **original** (pre-edit) title and time. A second delete was needed to remove it.
- **Root cause (code-traced):** editing a recurring occurrence materializes it into a `LessonInstance` override (id changes `lesson-<id>-<date>` → `lessoninstance-N`). `remove_class_service` then takes the `LessonInstance` + `scope="single"` branch, which does a bare `obj.delete()` (`lesson_service.py:759`) and **does not add a recurrence exclusion for that date**. The parent recurring `Lesson` therefore re-projects the occurrence with its original values. Contrast the `Lesson` + `scope="single"` branch, which correctly calls `split_lesson(..., remove_current_date=True)` to exclude the date — so the two delete paths are asymmetric.
- **Fix direction:** deleting a single `LessonInstance` that overrides a recurring `Lesson` must also exclude that date from the parent recurrence (or route through the same split/exclusion logic).
- **Repro confidence:** observed once end-to-end by the exploratory agent (with server-side confirmation); a *simplified* retest (non-recurring class, title-only edit) did not reproduce — consistent with the root cause (needs a recurring parent + a materialized override). Code path confirms the mechanism.
- **Impact:** a coach deletes a class and it silently comes back → data-integrity / trust defect on a core flow. → **P1.**

### FB-3 — Unread message count never clears for ~1 hour after a message is sent · **P1** · FILED PAD-66
- **Where:** `/messages`, `/dashboard`, both coach and student. Any message sent live through the app.
- **Symptom (exploratory):** recipient opens the conversation; `POST /api/app/conversation/<id>/read → 204`; the list badge clears while the thread is open but the message stays unread in the backend, the global unread count stays 1, and the badge reappears on navigating away/back. Seeded messages clear correctly; only app-sent ones stick.
- **Deterministic repro (this run):** sent coach→student, then `GET /messages/unread_count` = `{"unreadCount":1}` **before and after** `POST /conversation/1/read → 204`; messages stayed `isRead:false, status:"delivered"`.
- **Root cause (DB-confirmed):** `create_message_service` stamps `sent_at` with **`datetime.now()`** (local WEST/UTC+1) — `messaging_service.py:47` — while `mark_conversation_read_service` sets `last_read_at = utcnow_naive()` (UTC) — `:200` — and the unread query is `sent_at > last_read_at`. DB rows this run: app-sent messages `sent_at = 10:42 / 10:44` (local) vs server UTC-now `09:51` and `last_read_at = 09:51` (UTC). So a just-sent message looks **~1 hour in the future** and cannot be marked read until real UTC time passes it (~an hour). Seeded messages (yesterday) are unaffected. (The model default is correctly `datetime.utcnow`; line 47 overrides it with local time.)
- **Fix direction:** use `datetime.utcnow()` / `utcnow_naive()` for `sent_at` at `messaging_service.py:47` to match the rest of the system.
- **Impact:** for ~1h after every message (always, in the +1 summer offset), the recipient's unread badge won't clear on read — core messaging UX visibly broken. → **P1.** (SSE stream health, delivery both directions, and seeded-message read all verified working.)

- **Concurrent-QA auth interference (environment, not a defect):** all browser tabs share one `localStorage.accessToken` on `localhost:8080`, so a logout/registration in one agent bounces every other agent's session. Journeys were sequenced to limit this; future sweeps should isolate browser profiles per agent.
- **Dev-server wedge under concurrent SSE load (harness limitation — actionable):** the QA backend is a single-process `flask run` (dev server). Each open SSE `/api/app/events` stream holds a thread; running several browser agents concurrently (each holding streams) exhausted the pool and transiently wedged the whole backend (33 established conns observed), which stalled the responsive + empty-state passes. **Recommendations:** (a) run QA against a **gunicorn**-backed server with worker/timeout config (as prod does), or (b) cap concurrent SSE-holding agents / ensure agents close EventSource streams, or (c) sequence journeys more (fewer simultaneous streams). This is a QA-harness robustness item, not a product defect — but it cost coverage this run.
- **The QA web dev server (Vite :8080) died once mid-run** and was restarted (iCloud/Vite watcher fragility per project memory). Earlier journeys had already completed; messaging was re-run after the restart. Consider a supervised/kept-alive web server for unattended runs.
- **known-failures.md:** removed the two stale web entries (US-48, US-16 — green 2 runs straight); added the PAD-24 stale-test entry.

### Notify journey (P2) + the "notify wedges the backend" near-miss (NOT filed — disproven in isolation)

The notify exploratory agent reported that clicking **Notify** on a class made `GET /notify/groups` and `POST /notify/manual` hang forever and then wedged the **entire** QA backend (all `/api/app/*` calls hanging for 90s+), and flagged it P0/P1. **On verification this did not hold up as a product defect:**

- **Isolated deterministic probe (no browser agents contending):** `POST /api/app/notify/manual {model:LessonInstance, originalId:1, date:2026-07-27, playerIds:[1]}` → **HTTP 200 in 0.28s** `{"sent":1}`; `GET /notify/groups` → **200 in 0.3s**; `healthz` stayed 200 throughout. The notify handlers do **not** block. (`send_push_notification` early-returns with no VAPID/subscriptions in QA; `get_notification_groups` is pure DB.)
- **Actual cause — dev-server wedge:** at the moment of the hang there were **33 established TCP connections to :5003**. The single-process `flask run` dev server holds a thread per open SSE `/api/app/events` stream; with several concurrent browser agents (coach + student + the responsive agent) each holding streams, the thread pool exhausted and *all* new requests queued and appeared to "hang" until connections freed — after which the server recovered on its own. This is the known **SSE/worker-exhaustion** pattern (prod was fixed with gunicorn worker/timeout config; the QA dev server has no such protection).
- **Verdict:** environment/test-harness artifact under concurrent load, **not** a notify product bug → **not filed**. Notify is verified working (`{"sent":1}`). Real takeaways in §4.

Because notify was verified functional in isolation and the wedge is environmental, the P2 `web-notifications-reminders` journey is treated as **PASS (notify sends; success-toast-in-UI unverified due to the concurrent wedge)**.
