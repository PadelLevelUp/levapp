## 2. Functional bugs (exploratory)

Two genuine functional defects were found by walking the live app. Neither is filed
(calibration run); both are candidates for the enforcement gate.

### FB-1 — Dark theme is a no-op (web)  ·  severity **P2**
- **Where:** Settings → Preferences → Theme = "Dark" (P1 journey `web-settings-language-theme`).
- **Repro:** Set Theme to Dark → "Save changes" → toast "Settings saved". App stays fully
  light. Reload `/settings` → still light, and the dropdown reverts to "System".
- **Evidence (DOM):** `<html>` has no `dark` class and no `data-theme`; `body` background
  stays `rgb(249,250,251)`; `getComputedStyle(html).colorScheme === "normal"`; **no theme
  key in localStorage**. So the preference neither applies to the DOM nor persists.
- **Contrast:** the **Language** switch on the same panel applies instantly and app-wide —
  so this is theme-specific, not a general "applies on save" pattern.
- **Impact:** dark mode is effectively unavailable on web. App remains fully usable in
  light mode → P2, not P1. (Also means the design-critique dark-mode pass could not run.)

### FB-2 — Evaluation "saved" but not persisted (web)  ·  severity **P1 (candidate)**
- **Where:** Player detail → "Add Evaluation" → "Save evaluation" (P1 journey
  `web-evaluation-notes`), tested on player `/players/31`.
- **Repro:** Open Add Evaluation (strengths/weaknesses pre-filled from the player's S&W,
  no numeric score entered) → "Save evaluation" → toast **"Evaluation saved"**. The
  Evaluation panel still reads "No evaluations yet." **After a hard reload it still reads
  "No evaluations yet."** — nothing was persisted.
- **Impact:** the coach receives a false success confirmation while the evaluation is
  silently dropped (perceived data loss on a core coaching flow). Likely the backend
  requires ≥1 score and rejects empty evaluations, but the UI reports success regardless.
- **Uncertainty:** needs backend confirmation of whether empty-score evaluations are
  intentionally rejected. Rated P1 for user impact; flagged for gate discussion because a
  scores-required rule would soften it to "misleading toast" (still a real defect).

## 4. Other observations (verify — not yet classified)

- **Recurring-class weekday discrepancy — ROOT-CAUSED → PAD-59.** The dashboard showed
  the recurring class on **Mon 20/27 Jul** instead of Tuesdays. Cause: the **E2E/QA seed**
  (`apps/web/e2e/scripts/seed.py:280`) builds `daysOfWeek` with Python `weekday()` (Tue=1),
  but the app's convention (backend `calendar_tools.py` WEEKDAY_MAP + frontend
  `domain.ts` + `getDay()`) is **0=Sunday** (Tue=2), so `1` = Monday. **Product recurrence
  logic is correct**; only the seed uses the wrong convention. Filed as **PAD-59**.
- **Register-link id ≠ detail-route id.** The player's register link is `/register/33`
  while the detail route is `/players/31`. Likely intentional (separate registration token
  vs. player id), noted so it isn't re-flagged.
- **New-class prefills today's date** regardless of which day/slot cell was clicked (minor
  UX; the clicked slot's date is ignored).
