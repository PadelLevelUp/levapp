## 1. Headline — three defects that explain "looks and feels noticeably worse"

These are not feature gaps. They affect **every screen** of the iOS app and are the most likely
cause of the reporter's overall impression.

### H1 `[iOS]` The whole app renders with no typographic weight hierarchy

`apps/mobile/src/components/ui/text.tsx` applies `font-sans` → `PlusJakartaSans_400Regular`, a
single registered PostScript face. `apps/mobile/tailwind.config.js` explicitly says weights must be
opted into by *family* (`font-sans-medium`, `font-sans-semibold`, `font-sans-bold`) because
"React Native does not synthesize weights for a custom family".

The app does the opposite almost everywhere: **108 uses of `font-bold` / `font-semibold` /
`font-medium`** (which only set `fontWeight` and leave the family at Regular) against **30** uses of
the `font-sans-*` utilities that actually work.

Visually confirmed in `06-settings.png`: the section titles "Perfil", "Preferências", "Calendário",
"Notificações"… (`app/(tabs)/settings.tsx:45`, `font-medium`) render at exactly the same weight as
their grey descriptions — no hierarchy at all. The only genuinely bold text on screen is the navy
header ("Definições"), which uses the **system** font via `headerTitleStyle`, not the brand face.
Same in `03-players.png` (player names, `font-medium`) and `04-messages.png`.

It also has a functional cost: in `04-messages.png` the conversation with 1 unread message is not
visually heavier than the read one — `conversation-item.tsx:53` asks for `font-semibold` and gets
Regular, so web's unread emphasis is simply absent on iOS.

**Mechanism, two alternatives ruled out.** It is *not* a font-loading bug — `app/_layout.tsx:60-67`
loads all six faces via `useFonts`. And family utilities demonstrably do work: in
`levapp-1.0.0/01-dashboard.png`, "Morning, Miguel" (`font-display text-xl` → `Poppins_700Bold`, a
**family** utility) renders genuinely heavy, while everything else on that same screen — all bare
weight utilities — renders Regular. Specify the family, get the weight; specify only `fontWeight`,
get Regular.

Worth 60 seconds on a simulator before a 108-site sweep: put `font-semibold` next to
`font-sans-semibold` on one screen. If they match, the cause is elsewhere (e.g.
`react-native-css-interop` dropping `fontWeight`) and the fix is different.

**Fix shape:** swap the weight utilities for the family utilities across `apps/mobile`, or make the
`Text` wrapper map `font-medium|semibold|bold` onto the right family.

### H2 `[iOS]` No date localization anywhere on iOS — dates render in English in a Portuguese app

> **Narrowed by §12/L6:** the week-range label (`17–23 Aug`) is English on **web too** — it comes from
> `packages/hooks/src/useCalendar.ts:76`, which hardcodes `locale: enGB`. The rest of this finding is iOS-only.

Web has `apps/web/src/lib/dateLocale.ts`, which maps `i18n.language` → a date-fns `Locale` and is
threaded through every `format()` call (PAD-52). **`apps/mobile` imports `date-fns/locale` zero
times** — all 16 distinct `format()` calls run with the default en-US locale.

Visible in `02-calendar.png` on a Portuguese device:

| Rendered on iOS | Should be (as web renders it) |
|---|---|
| `MON TUE WED THU FRI SAT SUN` | `SEG TER QUA QUI SEX SÁB DOM` |
| `17–23 Aug` | `17–23 ago` |
| `Sunday, 23 August` | `domingo, 23 de agosto` |

Plus `04-messages.png`: `21 Aug` / `20 Aug` in the conversation list.

Related, same class: `src/features/messages/utils.ts:63` returns a hardcoded `"Yesterday"` string
where web uses `t("messages.yesterday")`.

## 12. Layout & density pass (added after the first report)

**Why this section exists.** The first pass audited structure, behaviour, i18n and typography — all
things a source diff catches. It did **not** cover screens that exist on both platforms but allocate
space differently. That gap was found by the reporter, not by the audit.

**Method.** Web driven at 440x956 and 390x844 (the iOS App Store screenshots are 1320x2868 = 440x956
@3x, so 440x956 is an exact geometric match), signed in as a coach, **in Portuguese**, against a
`levelup_audit` database seeded from the E2E fixtures (~30 players, matching the screenshots'
density). Web numbers are `getBoundingClientRect()` from the live DOM; iOS numbers are pixel-row
scans of `levapp-1.1.0-pt/*.png` divided by 3.

### L1 `[iOS]` The calendar split is 50% on web and 19% on iOS

The reporter's observation, confirmed and quantified.

Web (`MobileCalendarView.tsx`) is a fixed two-way flex split — `flex-1` on the week strip and
`flex-1` on the day detail — so the strip gets **exactly half** the space below the toolbar at any
data density. Measured: 50.2% at 390x844, 50.1% at 440x956.

iOS (`app/(tabs)/calendar.tsx`) is not a split at all: `WeekStrip` renders above a `ScrollView` and
is **content-sized**, growing with the busiest day and capped at `MAX_CHIPS = 4`.

Like-for-like at 440x956, with the same density (busiest day = 2 chips):

| Band | Web | iOS |
|---|---|---|
| Top chrome | 48pt | 100.7pt |
| Week-nav row | 122pt (toolbar, incl. legend) | 36pt |
| **Week day-columns** | **362pt** | **139.7pt** |
| Day detail | 361pt | 596pt |
| Bottom nav | 64pt (auto-hides on scroll) | 84pt (fixed) |

Day-columns as a share of the area below the nav row: **web 50.1%, iOS 19.0%** — 2.6x less space for
the week overview on the same data.

It does not converge at maximum density either: iOS at 4 chips is roughly 4x32 + gaps + ~70 header
= ~212pt, still below web's 362pt.

**`WeekStrip.tsx:36-43` documents this deviation backwards.** It says the strip is "a bigger share of
the screen than web gives it" and suggests lowering `MAX_CHIPS` to 3 "if the detail list feels
squeezed". Both are the wrong way round at every density. That comment will mislead the next reader
and should be corrected along with the layout.

### L2 `[iOS]` iOS spends ~73pt more on fixed chrome, on every screen

Web mobile: 48pt header + 64pt bottom nav = 112pt, and the bottom nav translates out of view on
scroll (`bottomNavHidden` in `AppLayout.tsx:291`), so content can reclaim it.

iOS: 100.7pt navy header + 84pt tab bar (`tabBarStyle: { paddingBottom: 24, height: 84 }`) = 184.7pt,
both permanent.

That is 7.6% of a 956pt screen given up before any content renders, and it compounds every per-screen
difference below.

### L3 `[WEB]` The web bottom nav overflows and clips on a 390px-wide phone

`AppLayout.tsx:293` renders all seven `visibleNavItems` in a `h-16` bar, each `min-w-[60px]`.
7 x 60 = 420px.

Measured at 390x844: `scrollWidth` 428 vs `clientWidth` 390 — **38px of overflow**, with the last
item ("Definições") ending at x=428, past the right edge. At 440x956 it fits (last edge 432 < 440).

390px is the standard iPhone width (12/13/14/15, and SE is narrower still); 440 is Pro Max only.
Portuguese labels are longer than English ones, which is the default locale.

**This corrects PAD-171**, which stated web "has the same seven as a vertical sidebar, so it does not
crowd". Web mobile has a bottom nav too, and it handles seven destinations *worse* than iOS: iOS
compresses (flex items, `paddingHorizontal: 0`), web clips.

### L4 Settings row density — same pattern, different weight

Both platforms use a drill-in (nav list -> tap -> pane). Verified on web at 440px: tapping a visible
nav row does open the pane, with a "Secções" back affordance. Not a divergence.

The rows differ: web is **36pt, label only** (7 rows = 276pt, 28.9% of the viewport); iOS is
**~64pt with a description line under every row** (~440pt, ~46% of the viewport). iOS is ~1.8x
taller per row. Neither is wrong — but it is why the iOS Settings screen reads as a heavier, more
crowded list, and it interacts badly with H1 (the descriptions and the titles render at the same
weight, so the extra text buys no hierarchy).

### L5 `[WEB]` Players — web pushes the first card 112pt further down than iOS

Web puts **437pt** of chrome above the first player card (header, page title, search, sort, two
warning banners); iOS starts its first card at **~325pt**, because the screen title lives in the navy
app bar instead of being repeated in the content. Card heights are comparable (web 114pt).

Density divergence in iOS's favour — worth noting because it shows the gap is not one-directional.

### L6 `[WEB]` + `[iOS]` The calendar week label is English on **both** platforms

`packages/hooks/src/useCalendar.ts:76-90` builds `weekLabel` with `{ locale: enGB }` hardcoded, in
three separate `format()` calls. Both shells consume this hook, so a Portuguese user sees
**"31 Aug–6 Sep"** on web and iOS alike.

This narrows H2: the *rest* of iOS's date problem is iOS-only (web renders "SEG TER QUA", "quarta-feira,
2 setembro" correctly while iOS shows "MON TUE WED", "Sunday, 23 August"), but this one string is a
shared-package bug and fixing it in `packages/hooks` repairs both at once.

### L7 `[WEB]` + `[iOS]` `sideLabel()` renders English on **both** platforms

`packages/types/src/domain.ts:11-19` defines `SIDE_LABELS` for `'en' | 'es'` only. Web calls
`sideLabel()` in four places — `PlayersPage.tsx:324`, `PlayerHeader.tsx:138`,
`EditPlayerSheet.tsx:165,293`, `StudentDetailSheet.tsx:70` — so web's player list shows **"Right"**
in Portuguese too, exactly like iOS.

**This corrects PAD-158**, which said web uses `t("players.sideRight")`. Web does have those keys, but
uses them only in the add/edit *selects*; the badges go through `sideLabel()`. So web is internally
inconsistent as well, and the fix belongs in `packages/types` for both shells.

Also: `StudentDetailSheet.tsx:70` passes `{ locale: 'es' }` — hardcoded **Spanish**. It is on the dead
`StudentsPage` (W1), so nobody sees it, but it should go with that deletion.

### L8 `[WEB]` Message timestamps use a 12-hour clock in Portuguese

Web's conversation list renders **"07:22 PM"** with the app in Portuguese; pt-PT uses a 24-hour clock.
(iOS renders `HH:mm` — correct here, though its date half is broken per H2.)

### Also confirmed visually

- Web's calendar toolbar carries the legend (Próxima aula / Cheia / Concluída / Evento / Confirmados),
  iOS has none — C4 / PAD-170, now with a screenshot.
- "0 aula" on web confirms the pt CLDR zero-plural issue on the calendar day header.
- Web calendar chips truncate mid-word ("E2E Declined Count… Class") under `line-clamp-3`.

### What this section did not cover

Class detail (web bottom Sheet vs iOS full screen), conversation detail, and Presences were not
measured — there are no iOS screenshots of them, and the simulator was not run. Those remain
code-derived only.

### 14.1 Deliverable 1 — the font mechanism is confirmed (gates PAD-156)

Five adjacent `<Text>` elements through the app's own wrapper (`src/components/ui/text.tsx`), all
`text-2xl`, all rendering the identical prefix `AaBb 123 —`, on the dashboard. **Three-way, not
two-way**: a control with no weight class at all, because `font-semibold` vs `font-sans-semibold`
alone cannot say which of the two is the anomaly. The edit was reverted in the same session; the
screenshot is `audit-2026-09-04-pt/06-font-mechanism.png` and is attached to PAD-156.

Ink density on the identical prefix (pixels darker than 120 in the line's row band, control = 1.00):

| Class on the `<Text>` | Ink vs control | Renders as |
|---|---|---|
| *(none — inherits `font-sans`)* | 1.00x | Regular |
| `font-semibold` | 1.03x | **Regular — indistinguishable from the control** |
| `font-sans-semibold` | 1.46x | SemiBold |
| `font-bold` | 1.03x | **Regular — indistinguishable from the control** |
| `font-sans-bold` | 1.62x | Bold |

### 14.4 A note on how this session was run

The mobile app's backend was run on port 5055 against a purpose-made `levelup_sim180` database rather
than on :5001 against `levelup_test`. Ports 5000/5001/8080 and `levelup_test` are shared by every
concurrent agent behind a single lock, and this session needed its servers up for well over an hour —
long past the ~25 minutes the lock is meant to be held. Running on an unshared port and an unshared
database made the lock unnecessary instead of held hostage. The trade is the one recorded in §14.2:
no Vite server, so no web-side comparison. Worth repeating for any future simulator session; worth
knowing that it is why the web half is missing.
