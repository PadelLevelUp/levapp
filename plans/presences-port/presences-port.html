Porting the Presences Tab

A full teardown of the Lovable Presence Overview prototype, matched feature by feature against what LevelUp already has — and what it would actually take to land it.

Reference reference/Presence Overview · ~2,060 LOC Investigated 6 parallel agents Date 25 Aug 2026

The prototype is a UI shell over static mock data — but our schema already models almost everything it displays. The reference has no backend at all: no fetch, no persistence, every coach edit lost on reload. What makes this port cheap is the other side: our Presence table already carries status, justification, invited, confirmed, validated and late_cancellation, and lessons.type is already Enum("academy", "private") — the exact split the prototype charts.

Every metric in its players table is derivable from tables we already have. Zero schema migrations are required, and marking a class validated already works — confirm_presences stamps validated=true on every row it writes. The real work is three read endpoints, one small write endpoint for un-validating, and a handful of product decisions.

What the prototype actually is

Three components and a page, sitting on two mock-data modules.

The Presences tab composes four blocks: a Validate Classes widget (a dialog-based inbox for finalising attendance, and by far the most substantial piece at 723 lines), a Players table with filtering, column toggles and CSV export, three Recharts visualisations, and four KPI tiles.

Its stack diverges from ours in ways that matter for porting: it runs TanStack Start (SSR meta-framework) rather than React Router, Tailwind v4 with CSS-first @theme and oklch tokens rather than our v3 config, and a Vite 8 / Rolldown / Nitro toolchain. None of that comes across. What does come across is the component logic and JSX — and helpfully, both codebases are on Recharts ^2.15.4, the identical version.

Note that the prototype's own domain model was clearly written with knowledge of ours. Its per-player metrics line up almost one-to-one with columns we already store.

Decisions needed before building

These are product calls, not engineering unknowns. Each one changes the spec. Four map to rows in the table above; naming is a fifth that sits across the whole feature.

1. What does "validated" mean at class level?

The reference validates a whole class. We store validated per player row. There's also a tempting third option: LessonInstance.status = 'completed', whose service function already exists but is unreachable dead code with no route.

That third option is a trap. specs/calendar/spec.md rule 11 guarantees an event's completed status is derived purely from the clock — letting a coach set it directly would violate an existing rule.

RecommendationDerive class validation from all(p.validated) over its presences. No new column, no rule violated.

2. Does validating lock the record?

"Validate" implies finality, but nothing in our tree enforces it — confirm_presences can be called repeatedly on a past class today. Meanwhile the reminder-decline path and the eligibility reader both touch these rows, and eligibility is specced to evaluate fresh, never snapshotted.

A lock introduced here could silently break those paths.

RecommendationDon't lock in v1. Keep the reference's own behaviour — Undo and Edit stay available — and state explicitly in the spec that validation is a finality marker, not a write barrier.

3. Should a self-declared absence default to justified?

The reference assumes yes. But unjustified_absences is a live input to the eligibility bar, so this default directly decides who stays eligible to join classes.

RecommendationYour call — it's a coaching-policy question, not a technical one. Whichever way it goes, the spec should say so out loud, because the eligibility spec silently depends on it.

4. Naming: "Presences" or "Attendance"?

Both terms are already live here. Presence is the canonical entity; attendance is the domain directory and the existing page name. The Portuguese product name for the shipped page is already Presenças.

RecommendationKeep Presence as the entity and attendance as the domain, and let "Presenças / Presences" be the user-facing tab name. Don't create a second specs/presences/ domain beside specs/attendance/.

5. Do table filters drive the charts?

In the reference they don't — the charts always show fixed aggregates regardless of what the table is filtered to. Two decoupled views of the same data on one screen tends to read as a bug.

RecommendationWire filters through to the charts, or visually separate the two zones so it's clear they're independent.

The plan

Four phases. Backend first here, because the frontend is additive and can't break anything that ships today.

1

Spec the feature

specs/attendance/spec.md · no code

Route through specflow-change-router first, as the project requires. This classifies as a New Feature with a spec-gap flavour — it fills in the validated field the schema already reserved but never specified.

Add a leaf — attendance.validation — to the existing attendance domain rather than a new one. Follow the tree's actual convention (one spec.md per domain, ## leaf headers, --- frontmatter), not the generic one-file-per-leaf template in the specflow skill docs — the real tree doesn't use it.

Record decisions 1–5 as rules. Avoid the word "retroactive": eligibility.enforcement rule 8 already uses it for an unrelated concept, and the collision will confuse anyone grepping the tree. Note that specs/ isn't under git, so the rules need reproducing in the PR body.

2

Backend: three reads and one write

levelup_backend · no migration

Paths follow the existing resource-first convention (/class_instance/presences/confirm, /attendance_history) rather than inventing a /presences/* prefix:

  • GET /class_instances/pending_validation — classes awaiting validation for a week, with rosters and per-player RSVP state. Promotes the dashboard's existing count into a real listing.
  • GET /presence_stats — the 8 per-player metrics. Must reuse compute_player_kpis()' predicate rather than recomputing, per the repo's single-source-of-truth rule.
  • GET /presence_trend — roster-wide time series. Generalise attendance_history_service to accept a coach and drop its hard status='present' filter.
  • POST /class_instance/<id>/presences/unvalidate — the only new write. Validating already works via confirm_presences; nothing anywhere sets validated back to false, which is what Undo needs.

All four sit in frontend_api.py behind require_coach(), but the guards differ by shape: the two class-scoped routes use require_owned_class(), while the two roster-wide ones have no class_id to check and instead scope the query to the coach's roster (require_own_roster_relation when a single player is requested). Coach-only throughout — the specs forbid exposing other players' presence data to a student.

3

Frontend: the tab

levelup_frontend/apps/web

  • Route + navItems entry, coach-gated.
  • Port the three blocks, re-skinned to LevApp tokens. Reuse AttendanceRow for the status toggle instead of porting a second implementation.
  • Build on TanStack Query hooks — the attendance area currently has none, so this also brings it in line with Players and Calendar.
  • Charts: isAnimationActive={false} on all three.
  • i18n: new src/locales/{pt,en}/presences.json. Verify layout in pt, not just en — Portuguese strings are wider and that's where overflow bugs actually show up. Watch for translated labels frozen in state; store the value, derive the label.
4

Verify

E2E + manual walk

Playwright spec covering the validate flow end to end, plus roster stats rendering. Seed data needs past classes with a mix of confirmed / declined / unanswered presences — worth checking whether the current seed has any completed classes at all.

Then a real browser walk of every changed flow before the PR. Automated green isn't the gate here.

Risks worth naming

  • The trend endpoint is the only real unknown. Everything else is mechanical; generalising a single-player service to roster-wide aggregation is where the estimate could move.
  • Two ways to mark attendance. After this ships, a coach can mark attendance from the class detail sheet or from the Presences tab. That's fine, but the spec has to say they're the same operation, or the tree ends up with two undifferentiated flows.
  • Batching backend migrations. Not applicable here — no migration — which conveniently sidesteps the multiple-heads failure mode that has taken prod down before.
  • Eligibility coupling. This tab makes absence counts visible for the first time. Expect the numbers to be questioned, and possibly to surface existing data-quality problems that were invisible while nothing read justification.
