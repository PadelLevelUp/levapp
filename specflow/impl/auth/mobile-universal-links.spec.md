# auth.mobile-universal-links


### Intent
An invite or activation link is a web URL. Tapping one on an iPhone that already has the app
installed opens Safari, so the person ends up completing registration on the web and then signing in
to the app separately — the app never gets to own the moment it was installed for.

iOS universal links fix this: the app claims the three account-creation paths, and iOS hands a tap on
one of them to the app instead of to Safari, with the token intact.

This spec covers the **link plumbing only** — the entitlement, the served association file, and the
path→route mapping. The native screens the arriving link lands on are `auth.mobile-account-creation`.

### Claimed paths
Exactly four on iOS: three account-creation entry points and the join link (PAD-212):

| Web path | Owner spec |
| --- | --- |
| `/invite/player/:token` | `players.invite-completion` |
| `/invite/coach/:token` | `clubs.coach-invitation` |
| `/register/:userId` | `auth.register` / `auth.activate` |
| `/join/coach/:token` | `players.join-token` (routed by the file route `app/join/coach/[token].tsx`, not by rule 3's parser) |

### Rules
1. The app claims `levapp.app` and `padellevelup.com` (`ios.associatedDomains` in
   `apps/mobile/app.json`: `applinks:levapp.app`, `applinks:padellevelup.com`,
   `applinks:www.padellevelup.com`). `apps/mobile/ios/` is
   gitignored and regenerated by `expo prebuild`, so this lives in config, never in Xcode.
2. Both domains serve `/.well-known/apple-app-site-association` over HTTPS as
   `Content-Type: application/json`, with no redirect and no authentication. The file declares
   `appIDs: ["9K2J8D2ARR.com.padellevelup.app"]` and claims exactly the four paths above — no
   broader wildcard, which would swallow every link on the domain into the app. Android claims the
   same four paths, the join link included (rule 7, AUTH-MOBILE-UNIVERSAL-LINKS-2; owner decision
   2026-11-10).
3. Path→route mapping is a pure function (`apps/mobile/src/lib/universalLinks.ts`). It accepts a full
   URL, a rooted path or a bare path; it percent-decodes the token; it ignores the query string and
   fragment, except the `t` of a registration link, which is the activation secret (`auth.activate`
   rule 8); and it returns nothing for an unknown path, a wrong segment count, a blank token, or an
   absolute URL on a host the app does not claim.
4. **What the two transports actually guarantee (corrected by PAD-326).** ~~Universal-link
   routing does not interact with push-notification tap routing. The two use different
   transports and disjoint route sets, so neither intercepts the other.~~ That claimed a
   property the code does not have, which is worth naming: **the parser's route set and the
   app's route set are not the same thing.** `parseUniversalLink` handles only the three paths
   above and returns nothing for anything else — but the app CLAIMS whole hosts
   (`levapp.app`, `padellevelup.com`, `www.padellevelup.com`), so iOS still opens the app for
   every URL on them, and a path the parser declines falls through to **expo-router's default
   path matching**, which resolves it against the app's own file-based routes. A link to
   `/class/5` in an email therefore reaches the class screen without the parser ever being
   consulted.
   What is guaranteed is narrower and true: **the parser never routes a path it does not
   handle, and it never intercepts a push.** Where an unhandled claimed-host path lands is
   decided by the app's routes, not by this module. Since PAD-326 that is a working
   destination for `/class/<id>` (`calendar.event-detail` rule 15) rather than a dead screen —
   but it is a fall-through, not a claim this spec makes, and any new app route silently
   becomes reachable from an email the day it is added.
5. This is additive. Universal links do not fire from every context — a URL typed into Safari's
   address bar, some in-app browsers, some QR scanners — so the web flow remains the fallback and is
   unchanged.
6. Each claimed route renders the native account-creation screen for that path — see
   `auth.mobile-account-creation`. (Until PAD-164 landed, the routes rendered a hand-off placeholder
   that reopened the equivalent web URL instead.)
7. **Android App Links (PAD-216).** `android.intentFilters` in `apps/mobile/app.json` claims the
   same four path prefixes as iOS, `/join/coach/` included, so a coach join link opens the app on
   Android as on iPhone (owner decision 2026-11-10). Code to follow: the Android app is not built
   yet and `app.json` claims only the three account-creation prefixes; the join prefix is added
   when the Android app is. It claims them on the same three hosts (`levapp.app`, `padellevelup.com`,
   `www.padellevelup.com`) in one `VIEW` filter with `autoVerify: true` and the `BROWSABLE` and
   `DEFAULT` categories; the same pure mapping of rule 3 routes them. Android only verifies the
   claim against `/.well-known/assetlinks.json` on each host, carrying the SHA-256 of the release
   signing certificate, which exists only once the owner creates the Play signing key. Until that
   file is served a tap opens the browser or the chooser, and the web flow of rule 5 is the
   fallback. The file is added in the change that has the real fingerprint — never with a
   placeholder, which would be a claim nobody can verify.

### Acceptance Criteria

#### AUTH-MOBILE-UNIVERSAL-LINKS-1: A claimed-host path the parser does not handle (PAD-326)
- **Given** a URL on a claimed host whose path is not one the parser handles — say
  `https://levapp.app/class/5`
- **When** it is tapped in Mail
- **Then** `parseUniversalLink` returns nothing and routes nothing

- **And** the app still opens, because the host is claimed, and expo-router matches the path
  against the app's own routes

- **Then** the destination is whatever that route renders — for `/class/<id>`, a class resolved
  from the id (`calendar.event-detail` rule 15), not a "could not find" screen

#### AUTH-MOBILE-UNIVERSAL-LINKS-2: Android declares the same four paths as iOS (PAD-216; rule 7)
- **Given** `apps/mobile/app.json`
- **When** `expo prebuild --platform android` generates the manifest
- **Then** the main activity has one `VIEW` intent filter with `android:autoVerify="true"`, the `BROWSABLE` and `DEFAULT` categories, scheme `https`, hosts `levapp.app`, `padellevelup.com`, `www.padellevelup.com`, and path prefixes `/invite/player/`, `/invite/coach/`, `/register/`, `/join/coach/` — and no broader path
- Code to follow: `app.json` still claims only the first three prefixes, and the test's `ENTRY_PATHS` checks only those three; `/join/coach/` is added to both when the Android app is built (owner decision 2026-11-10)

#### AUTH-MOBILE-UNIVERSAL-LINKS-3: A player invite link opens the app at the right route
- **Given** an iPhone with the app installed and the association file served from `levapp.app`
- **When** the user taps `https://levapp.app/invite/player/abc123` from Messages
- **Then** the app opens rather than Safari
- **And** it lands on the player-invite route with token `abc123`

#### AUTH-MOBILE-UNIVERSAL-LINKS-4: Without the app installed the link still reaches the web flow
- **Given** an iPhone without the app installed
- **When** the user taps `https://levapp.app/invite/player/abc123`
- **Then** Safari opens the existing web player-invite page, unchanged

#### AUTH-MOBILE-UNIVERSAL-LINKS-10: The association file claims exactly the four paths (rule 2)
- **Given** `apps/web/public/.well-known/apple-app-site-association`
- **When** its `applinks.details` are read
- **Then** the one detail claims `/invite/player/*`, `/invite/coach/*`, `/register/*` and `/join/coach/*`, and nothing else

#### AUTH-MOBILE-UNIVERSAL-LINKS-5: The association file is served correctly from both domains
- **Given** a deployed production frontend
- **When** `GET /.well-known/apple-app-site-association` is requested on `levapp.app` and on
  `padellevelup.com`
- **Then** each responds `200` with `Content-Type: application/json`, no redirect, and a body listing
  the four claimed paths

#### AUTH-MOBILE-UNIVERSAL-LINKS-6: An unclaimed host is not treated as one of ours
- **Given** a link `https://evil.example.com/invite/player/abc123`
- **When** the path parser is asked to resolve it
- **Then** it resolves to nothing, and no route is opened

#### AUTH-MOBILE-UNIVERSAL-LINKS-7: A malformed link does not open a tokenless web page
- **Given** a link whose token segment is missing or blank (`/invite/player/`)
- **When** the route renders
- **Then** it shows the invalid-link state, and no web URL is opened

#### AUTH-MOBILE-UNIVERSAL-LINKS-8: Push routing is unaffected
- **Given** a push notification whose payload routes to `/conversation/7`
- **When** the user taps it
- **Then** the conversation opens as before; the universal-link parser claims neither
  `/conversation/:id` nor `/class/:id`

#### AUTH-MOBILE-UNIVERSAL-LINKS-9: The path parser maps each claimed path to its route, and nothing else (rule 3; auth.activate rule 8)
- **Given** a link on a claimed host, as a full URL, a rooted path or a bare path
- **When** the app parses it
- **Then** `/invite/player/<token>`, `/invite/coach/<token>` and `/register/<id>` each give their route, with the token percent-decoded, its letter case kept, and a trailing slash ignored; the host is matched in any case, with or without `www.`
- **And** the query string and fragment are ignored, except that a registration link keeps its `t` as the activation secret, a blank `t` reading as none
- **And** an unclaimed or lookalike host, an unknown path, a missing or blank token, or an extra segment gives nothing

### Notes
The host nginx that terminates TLS in front of the frontend container lives in no repository. The
container-level content-type block is in `apps/web/nginx.conf`; the VM-level step, the verification
commands, and the physical-device test plan are written down in `docs/infra/universal-links.md`.

The same SPA fallback (`try_files … /index.html`) is why a missing `/brand/*` asset used to answer
**200 `text/html`** — invisible to any check that asserts a 2xx, visible only to a human reading a
mail with a broken image (PAD-251, B-043). `location /brand/ { try_files $uri =404; }` keeps the
brand assets that transactional mail loads (`auth.email-verification` rule 7) off the fallback, so a
missing file is a 404. An availability check on those URLs asserts `Content-Type: image/*`, not
the status code.

Adding the associated-domains entitlement forces a new provisioning profile at archive time — the
same class of problem as `aps-environment`, which only flips to production at `-exportArchive`.
Verify against the exported `.ipa`, not the `.xcarchive`.

`WEB_APP_URL` currently points at `https://www.padellevelup.com`. Apple does not treat
`applinks:padellevelup.com` as covering the `www.` host; if www becomes the canonical link host the
entitlement needs its own entry. Tracked in `docs/infra/universal-links.md`.
- OPEN: Android `assetlinks.json` on `levapp.app` and `padellevelup.com` needs the release signing certificate's SHA-256 (owner prerequisite, PAD-216 store README).
- Decided 2026-11-10 (owner): Android claims `/join/coach/*` as iPhone does, so the two platforms open the same links in the app (rules 2 and 7). This closes the last open question in this spec.
