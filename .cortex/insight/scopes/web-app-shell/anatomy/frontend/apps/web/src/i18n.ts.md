## Purpose

Bootstraps and configures the app-wide `i18next` instance (PAD-40/PAD-39). Eagerly globs every locale JSON file under `src/locales/<lng>/<area>.json`, deep-merges the per-area files into one `translation` namespace per language, and initializes `i18next` with `pt` as both default and fallback language. Also keeps `<html lang>` in sync with the active language. This is the single source of truth for which languages the app supports and where their strings come from — new screens are localized purely by adding a JSON file, never by editing this module.

## Main players

- `Dict` (line 14) — `Record<string, unknown>` type alias for a loosely-typed JSON blob.
- `modules` (lines 20–25, critical) — `import.meta.glob<{ default: Dict }>("../../../src/locales/*/*.json", { eager: true })`. Eager (not lazy) so every locale ships in the initial bundle — no async translation loading. The three-levels-up path is called out in a comment: the monorepo restructure (PR #47) moved this file to `apps/web/src/` but left the locale tree at the repo-root `src/locales/`.
- `deepMerge(target, source)` (lines 28–46, critical) — recursively merges plain-object values key by key; non-object values (including arrays) overwrite rather than merge. Used to combine multiple per-area JSON files (`nav.json`, `players.json`, …) into one flat `translation` tree per language without one file clobbering another's sibling keys.
- The module-load loop (lines 50–58, critical) — iterates `modules`, extracts the language segment from the glob path via regex `/\/locales\/([^/]+)\//`, and deep-merges each file's default export into `resources[lng].translation`.
- `SUPPORTED_LANGUAGES` / `AppLanguage` (lines 60–61) — `["pt", "en"] as const` and its derived union type; the app-wide list of valid language codes.
- `i18n.use(initReactI18next).init(...)` (lines 63–70, critical) — the actual i18next initialization: `lng: "pt"`, `fallbackLng: "pt"`, `supportedLngs`, `interpolation.escapeValue: false` (React already escapes), `returnNull: false` (missing keys return the key string, not `null`).
- `syncDocumentLang(lng)` (lines 76–80) — sets `document.documentElement.lang`. Called once at load with the initial language and wired to the `languageChanged` event (line 82) so it stays current across language switches.

## Insights

- The `pt` fallback is a locked product decision (PAD-39), not a default someone can casually change — a related memory records that pt's CLDR plural rules put `0` in the "one" category, so counted strings render "0 aula" unless an empty state gets its own translation key.
- `syncDocumentLang` exists to fix a real accessibility bug: `index.html` hardcoded `lang="en"` while the app defaults to pt, so screen readers announced Portuguese content with English pronunciation rules and browsers offered to "translate" pt into pt.
- Because the glob is eager, adding a new locale file increases the initial JS bundle size — there is no code-splitting per language.
- This module is imported for its side effect (`i18n.use(...).init(...)` runs at import time) in addition to its default export; `main.tsx` imports it as `import "./i18n"` (no binding) purely for that side effect, while other files import the configured `i18n` object directly (e.g. `AuthContext.tsx`, `dateLocale.ts`, `SettingsPage.tsx`).

## Query pointers

If you need to add a new UI language, read this file (extend `SUPPORTED_LANGUAGES`) together with `src/locales/<new-lng>/*.json` (outside this scope) and `dateLocale.ts`'s `LOCALE_MAP` (date-fns locale mapping — a language with no date-fns entry silently falls back to `pt` formatting). If you need to add translated copy to an existing screen, you only need a locale JSON file — this module never needs editing for that case.
