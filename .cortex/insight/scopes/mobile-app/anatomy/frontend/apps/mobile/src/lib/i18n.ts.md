## Purpose

Initializes i18next for the mobile app, sourcing translation strings from the monorepo-ROOT `src/locales/<lng>/<namespace>.json` files — the same tree `apps/web` reads — via 32 STATIC imports (16 namespaces × 2 languages), deep-merged per language into one `"translation"` resource. Initial language is device locale (`expo-localization`); `AuthContext` overrides it once the signed-in user's persisted `language` preference is known.

## Connections

Uses:
- `frontend/src/locales/{en,pt}/{auth,availability,calendar,classDetail,common,dashboard,messages,misc,nav,notificationsUi,players,presences,settings,students,training,ui}.json` (all resolved by L1 — 32 genuine structural edges, listed individually in `edges_crossing_scope` since the locale tree lives outside this scope): the raw translation dictionaries, deep-merged via `deepMerge`.
- `expo-localization`, `i18next`, `react-i18next`: outside this scope, third-party.

Used by: no in-scope file is captured in L1's structural edges (the `@/lib/i18n` / `.` default-export alias goes unresolved), but by direct reading this module's side effect (i18next init) is triggered by `app/_layout.tsx`'s side-effect import, and its default-exported `i18n` instance is used directly by `frontend/apps/mobile/src/auth/AuthContext.tsx` (`i18n.changeLanguage()`).

## Insights

- STATIC imports are a deliberate divergence from web: web's `apps/web/src/i18n.ts` (outside this scope) uses Vite's `import.meta.glob` to load namespace files dynamically, which has no Metro equivalent — Metro's static bundling requires each namespace file to be imported by name. `metro.config.js` already watches the whole workspace root for the raw-TS `@levelup/*` packages, so these cross-app-boundary relative imports (`../../../../src/locales/...`) resolve and hot-reload the same way.
- `fallbackLng` is `"en"` here but `"pt"` on web (per a comment, PAD-39, "locked") — an intentional, documented platform divergence: every existing mobile screen predates the i18n retrofit and is hardcoded English, so an English fallback degrades gracefully for any key not yet translated on mobile, whereas web's decision reflects its own (different) coverage state.
- Adding a NEW locale namespace requires FOUR edits to keep both languages in sync: the `en` import, the `pt` import, and both namespace-array entries (`enNamespaces`/`ptNamespaces`) — missing one silently drops that namespace's keys for one language rather than erroring, since `t()` calls for a missing key just render the raw key path.
- `compatibilityJSON` is left at i18next's current (ICU/Intl-based) default rather than the legacy `v4` shim, per a comment noting RN 0.81's Hermes ships with sufficient ICU/`Intl.PluralRules` support.

## Query pointers

If a translated string renders as a raw dotted key path (e.g. `"messages.blockSuccess"` literally on screen) on mobile but works on web, the namespace is very likely missing from one of the two import blocks or one of the two `*Namespaces` arrays here — check both languages' arrays, not just the language currently active.
