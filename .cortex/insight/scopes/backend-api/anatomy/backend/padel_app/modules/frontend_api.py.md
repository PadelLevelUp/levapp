## Purpose

The main `/api/app/*` REST surface for both the web and mobile frontend apps — calendar, dashboard, players, messaging, coach invitations, player invitations, class CRUD, attendance/presence reporting, bulk import, and training/exercise planning. Nearly every route is a thin `@jwt_required()` wrapper delegating to a service module (`lesson_service`, `player_service`, `messaging_service`, `training_service`, etc.); this file's own weight is in its authorization helpers and the historical trail of comments recording exactly which routes were unauthenticated or IDOR-vulnerable before PAD-92/PAD-103/PAD-115/PAD-116 closed them, several with the vulnerable route deleted outright rather than guarded because no real client called it.

## Main players

- `require_coach()` / `current_coach()` / `current_player()` / `current_user()` / `current_club()` (lines 166-251) — critical. The role-resolution core: `current_*` cache onto `flask.g` per-request; `require_coach()` 403s a caller with no coach profile (PAD-103, PAD-116) instead of letting `coach.id` raise `AttributeError` into an unhandled 500. `require_coach()`'s docstring is authoritative and names the exact six student-serving routes that must NOT be converted to it (`/calendar`, `/dashboard`, `/class_instance`, `/calendar_event`, `/lesson_instance/<id>/presences`, `/availability_blockers`), backed by `test_training_players_role_authz.py`.
- `assert_acting_coach` / `_required_int_id` / `require_owned_class` / `require_own_roster_relation` / `require_accessible_exercises` / `require_owned_training_target` (lines 254-393) — critical. The PAD-92 ownership-authorization toolkit: every mutating coach route uses one of these to verify the JWT's coach actually owns the row a body id references, rather than trusting a body-supplied `coachId`/`playerId`. `require_accessible_exercises` is all-or-nothing (one unreachable exercise id 403s the whole batch) and checks both shared-library access (`Association_CoachExercise`, any role) and direct ownership (`Exercise.owner_coach_id`), closing the gap for exercises created through the generic admin CRUD that never got an association row.
- `GET /events` `events` (SSE, lines 400-425) — critical. Long-lived Server-Sent-Events stream; the `q.get(timeout=15)` keep-alive loop exists specifically to detect a dead client (a write-only failure is otherwise silent) — the comment cites a real prod outage (2026-06-10/11) where a missing timeout let closed tabs leak gunicorn threads until the worker pool starved.
- `GET /calendar` `calendar`, `GET /lesson_instances` `get_lesson_instances`, `GET /calendar_event` `calendar_event`, `POST /class_instance` `class_instance` (lines 439-830) — critical. The calendar read surface; branches on `current_coach() is None` to also serve students their own data (the documented exception to `require_coach()`), and `calendar_event`/`class_instance` do per-row ownership checks (coach owns it, or student is enrolled in it) rather than blanket role checks, since PAD-92 found these used to hand any calendar row to any caller by id.
- `_resolve_attendance_subject` / `_parse_attendance_bound` / `GET /attendance_history` / `GET /absence_history` (lines 840-952) — critical. Shared authorization for "whose attendance can I see": self first (so a user with both a coach and player profile is never 403'd on their own data — coach-first ordering elsewhere in the file would do exactly that), then coach-of-roster. `absence_history` deliberately reuses both helpers rather than reimplementing them, since a parallel copy is exactly how the two routes' authorization would drift apart.
- `_presence_overview_range` / `GET /presence_stats` / `GET /presence_trend` / `GET /class_instances/pending_validation` / `POST .../unvalidate` (lines 955-1054) — critical (PAD-140). Roster-wide, coach-only presence reporting; the range defaults to trailing 90 days (vs. attendance history's current-month default) because a roster-wide trend needs more data to read.
- `POST /class_instance/presences/confirm` `confirm_presences` (lines 1412-1468) — critical. Marks attendance and, for newly-absent players on a future class, either creates a semi-automatic replacement-approval bundle or directly triggers waitlist invitations (only if the invitation window has already opened — otherwise the scheduler's own invite_start job picks it up later); swallows and rolls back on a `trigger_invitations` exception so a notification failure doesn't fail the attendance save itself.
- `_assert_owns_class_payload` / `POST /edit_class` / `POST /remove_class` (lines 1475-1508) — critical. Resolves and ownership-checks the target lesson/instance BEFORE the service mutates anything — malformed payload shape still 400s (not 403) so authorization failures aren't confused with bad requests.
- `POST /check_field_available` `check_field_available` (lines 1530-1604) — critical. Two distinct check kinds sharing one endpoint: hard DB-uniqueness (username/email, global, blocking) vs. soft duplicate-name warnings (PAD-17, case-insensitive, scoped to the requesting coach's own roster — a global match previously produced cross-club false positives). If no scope is supplied for the warn check, it skips silently rather than falling back to a global match (which would resurface the false positive).
- `add_player` / `edit_player` / `remove_player` / `delete_coach_level` / `delete_evaluation_category` / `delete_coach_note` (lines 1607-1690) — critical. All PAD-92 hardened: each pins the acting coach to the JWT and verifies roster/ownership before delegating to a service, replacing routes that used to accept an arbitrary `coachId`/`id` from the body.
- `_TABLE_MAP` / `import_analyze` / `_run_import_confirm` / `import_confirm` / `import_confirm_stream` (lines 1698-1887) — critical. The AI-assisted bulk-import pipeline's confirm stage: `_TABLE_MAP` fixes a dependency-safe import order (reference data → players/classes → associations → presences/evaluations/notes); `_run_import_confirm` is a generator shared by both the JSON (`/import/confirm`) and SSE (`/import/confirm/stream`) endpoints, yielding progress events so a large import doesn't idle out the gateway — `bulk_create_players` additionally supports row-level progress streaming (`stream=True`) since it's flagged as the reported slow path.
- `POST /class_instance/training/confirm` `confirm_training` (lines 2010-2032) — critical (PAD-115). All three checks — resolve, own, validate exercise ids — must run BEFORE `confirm_training_service`, because that service deletes the existing plan before inserting the new one; a late-running guard would still leave a materialized `LessonInstance` behind (from `require_owned_training_target`'s on-demand materialization) and could wipe another coach's plan before rejecting the request.

## Insights

- The file's comment trail (PAD-92, PAD-103, PAD-115, PAD-116) is itself the most reliable map of this blueprint's past IDOR/auth history — several routes (`POST /club`, `/user`, `/player`, `/coach`, `/coach_level`, `/lesson`, `/calendar_block` creation; `POST /user/<id>`, `/club/<id>`, `/lesson/<id>`, `/lesson/<id>/status` edits) were deleted outright rather than guarded, specifically because grepping every client repo (web, mobile, issue bot, Playwright, seed scripts) found zero callers — the fix was to shrink the attack surface, not add a decorator to unused code.
- `require_coach()`'s "do not convert" list is enforced by a named test file (`test_training_players_role_authz.py`), making the list executable rather than just advisory — a change to any of those six routes' auth model should update that test, not just this docstring.
- `confirm_presences`'s exception handling around `trigger_invitations` (lines 1459-1462) deliberately treats invitation-sending as best-effort relative to the attendance write: a failure there rolls back only the notification-side session state and still returns the (already-committed) presence data, so a coach's attendance marking never fails because the notification engine had a bad moment.
- `check_field_available`'s two check kinds share one endpoint and one 409 status code but mean different things to the frontend (hard-block vs. soft-warn) — the authorization comment is explicit that this distinction is a frontend-side interpretation of the same wire shape, not something the backend enforces by different status codes.
- `from padel_app.models import *` (line 9) is a wildcard import — every model name (`Lesson`, `LessonInstance`, `Presence`, `User`, `Coach`, `Player`, `Association_CoachPlayer`, `CalendarBlock`, `Conversation`, `CoachLevel`, `EvaluationCategory`, `CoachPlayerNote`, `MODELS`, `Association_CoachExercise`, `Exercise`, etc.) used throughout this 2000+ line file resolves through that single line, so tracing "where does `Lesson` come from here" requires knowing the models package's `__init__.py` re-export list, not a local `from padel_app.models import Lesson`.

## Query pointers

If you're adding a new coach-only mutating route, also read: the PAD-92 authorization-helper block (lines 254-393) and pick the matching helper — `require_owned_class` for lesson/instance targets, `require_own_roster_relation` for player-scoped writes, `assert_acting_coach` whenever a legacy body field like `coachId` must still be accepted but only as an assertion.
If you're touching a route that must serve BOTH coaches and students, read first: `require_coach()`'s docstring (lines 230-251) — the six-route exception list — before converting a `current_coach() is None` branch to a hard `require_coach()` call.
If you're debugging the SSE `/events` endpoint or a thread-leak/worker-starvation symptom, read: the keep-alive comment at lines 404-408 and `padel_app/realtime.py` (outside this scope).
If you're changing the bulk-import pipeline, also read: `_TABLE_MAP`'s ordering comment and `padel_app/services/import_service.py` (outside this scope) — the per-table order encodes real FK dependencies, not just a UI preference.
