## Purpose

The largest and highest-centrality test file in the notification-engine test suite: full-DB integration tests (real SQLite in-memory `app` fixture, `publish`/`send_push_notification` patched) for the class-reminder lifecycle in `notification_service` — sending reminders, repeat/follow-up reminders and their supersede/expiry bookkeeping, responding to a reminder (yes/no), the standing (permanent) waiting list CRUD, and the PAD-35/PAD-44/PAD-100 student-initiated attendance-cancellation flow. It is also the shared fixture library for the rest of the reminder/notification test suite: `test_notification_localization.py`, `test_reminder_response_idempotency.py`, and `test_scheduler_job_lifecycle.py::TestSendClassReminders` all import its seed helpers (`_seed_coach_and_student`, `_seed_instance`, `PATCHES`, `_config_with_repeat`, `_enable_auto_notify`, `_seed_replacement_candidates`) directly rather than redefining them.

## Main players

- `_seed_coach_and_student(app)` (24-63) — critical shared fixture: creates a coach user, coach, student user, and player; returns a dict of the four ids. The base seed every test class in this file (and several other files) builds on.
- `_seed_instance(app, coach_id, student_id, start_offset_hours=48)` (66-122) — critical shared fixture: creates a club, a `CoachLevel`, a `Lesson`, a `LessonInstance` at `now + start_offset_hours`, wires the coach and enrolls the student. Returns `instance_id`.
- `PATCHES` (125-128) and `_no_io` (131-140) — the two `unittest.mock.patch` targets (`notification_service.publish`, `notification_service.send_push_notification`) every I/O-touching call in this file (and imported into other files) must wrap; `_no_io` is a decorator wrapper around them (mostly superseded by the inline `with patch(...), patch(...):` idiom used throughout the file itself).
- `class TestSendClassRemindersIntegration` (147-281) — critical: `send_class_reminders` creates a `Presence` + one reminder `Message` per enrolled player; is a no-op for a class already started; is idempotent (no duplicate `Presence` on a second call); and does not crash when an enrolled player's user has `status=inactive` (the "ghost player" case).
- `class TestReminderTemplateResolution` (292-420, PAD-37) — critical: the scheduled reminder path renders the coach's custom `messageTemplates.reminder`/`reminder_followup` when configured, and falls back to the (locale-aware, PAD-39) default ONLY when no custom template exists for that key; a partial `messageTemplates` config (only `reminder` set) still merges correctly.
- `_config_with_repeat(app, coach_id, *, count, hours)` (421-435ish) — persists a `NotificationConfig` with `reminder_timing.reminderCount`/`hoursBetweenReminders`. Used across most of the rest of the file and re-imported by `test_reminder_response_idempotency.py`.
- `class TestRepeatReminders` (441-549) — critical: with `reminderCount=N`, successive `send_class_reminders` calls send up to N reminders then stop (4th call returns `{"sent": 0, "more_due": False, "blocked": []}`); a student confirming or declining halts further reminders early; `more_due` is `True` until the last configured reminder fires. The `blocked: []` field in the return contract was added by PAD-107/PAD-112 (see `test_student_availability_blockers.py`, `test_student_notification_block_preferences.py`).
- `class TestReminderSupersede` (551-657, PAD-49) — critical: sending a new reminder marks all PRIOR un-actioned reminders for that `(player, instance)` `msg_metadata["superseded"] = True` so the frontend disables their buttons, while the latest reminder and any ALREADY-RESPONDED-TO reminder are never marked superseded — superseding only ever touches responded-falsy messages.
- `_seed_replacement_candidates(app, coach_id, n=3)` (659-684) and `_enable_auto_notify(app, coach_id)` (686-693) — shared fixtures for invitation-engine tests; re-imported directly by `test_reminder_response_idempotency.py`.
- `class TestPastClassReminderExpiry` (695-888, PAD-68) — critical: once a class has started, a late response must NOT fan out replacement invitations, NOT create/reopen a vacancy, and NOT retroactively rewrite the coach's own attendance record (a late "no" cannot override a coach-marked "present"); the un-actioned reminder itself is marked BOTH `superseded` and `expired` (but never `responded`); `trigger_invitations` and the low-level `_send_invitation_batch` chokepoint both refuse to act for a past class (the latter actively expires an already-open `Vacancy` instead of inviting); a guard-rail test confirms the expiry check does not break the normal in-time response path.
- `class TestResponseAlwaysRecorded` (890-956, PAD-69) — a student's answer must always be durably recorded even if the `Presence` row was somehow missing when they answered (previously silently dropped, causing a spurious follow-up reminder); plain regression guard that a decline stops follow-ups.
- `class TestRespondToReminder` (958-1085) — critical: "yes" sets `Presence.confirmed=True` but leaves `status` untouched (coach still controls attendance) and creates no `Vacancy`; "no" sets `status="absent"`, `justification="justified"`, `confirmed=True` and ALWAYS creates a `Vacancy` immediately (even before the invitation window opens, so the scheduler finds it once the window arrives) but only sends `NotificationEvent`s once that window has actually opened.
- `class TestStandingWaitingListCRUD` (1087-1212) — `add_standing_waiting_list_entry`/`remove_standing_waiting_list_entry`/`get_standing_waiting_list` CRUD, including a migration regression (`.save()` on `StandingWaitingListEntry` writing `updated_at` must not raise), deactivation of a prior active entry when a new one is added for the same `(coach, player)`, and fan-out to a `WaitingListEntry` for an already-materialized future instance.
- `class TestCancelAttendance` (1214-1582, PAD-35/PAD-44/PAD-100) — critical, largest block: students may cancel a CONFIRMED attendance any time before class start (`cancel_attendance`), reverting `Presence` to `status="absent"`/`justification="justified"` and freeing the spot exactly like a reminder decline; after start it's a `409 Conflict` and the presence is left untouched (`late_cancellation` stays `False`); cancelling inside the coach-configured `cancellationDeadlineHours` window (default 24h) but before class start is still allowed but flagged `late_cancellation=True`, and the spot is still freed either way. PAD-44: cancelling produces exactly ONE coach-facing text `Message` (metadata `cancellation: True`) plus exactly one push targeted at the coach, worded differently for late vs. non-late. PAD-100: both the late and non-late coach notifications are fully localized when the coach's `language="pt"` — asserts specific PT strings present (`"cancelou"`, `"(ATRASADO)"` for late, `"para"`, `"às"`) and asserts a list of English fragments (`"cancelled"`, `"(LATE)"`, `" for "`, `" on "`, `" at "`) are absent, guarding against partial-localization leaks. Final test pins `cancellationDeadlineHours` defaults to 24 and round-trips through `get_config_dict`/`update_config`.

## Insights

- This file is the DE FACTO shared-fixture module for the reminder/notification test suite even though `conftest.py`/`helpers.py` (scope `backend-tests-a`) are the nominal shared-fixture files — three other test files import directly from it rather than from conftest, which means changing any of `_seed_coach_and_student`, `_seed_instance`, `PATCHES`, `_config_with_repeat`, `_enable_auto_notify`, or `_seed_replacement_candidates` here has blast radius beyond this file.
- The `blocked: []` field on `send_class_reminders`'s return dict (asserted throughout `TestRepeatReminders`) is a contract shared with two entirely different blocking mechanisms (PAD-107 calendar unavailability, PAD-112 notification preferences) implemented in later files — this file predates both but its assertions already encode the final three-key shape (`sent`, `more_due`, `blocked`).
- The reminder-decline vacancy-creation timing split (`TestRespondToReminder`) is a subtle two-phase design: a `Vacancy` is always created immediately on decline regardless of whether the invitation window is open, but `NotificationEvent`s (actual invites) are gated separately by whether `now` is past the window — this decouples "the spot is officially open" from "candidates have been contacted."
- `TestCancelAttendance`'s PT-localization tests assert both presence AND absence of strings (PT words present, specific English fragments absent) rather than just presence — this is the same anti-partial-localization pattern used in `test_notification_localization.py` and `test_notification_i18n.py`, applied to a third message type (coach-facing cancellation notices) that neither of those files covers.
