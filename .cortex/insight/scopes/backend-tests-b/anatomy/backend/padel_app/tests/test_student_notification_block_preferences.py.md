## Purpose

PAD-112 tests: a student can block class-vacancy invitation notifications outright via three independent `User` flags (`notif_block_auto_invitations`, `notif_block_manual_invitations`, `notif_block_all`) plus a free-text `notif_block_reason`, each enforced at a different point in `notification_service`. Pins each level's enforcement point and independence from the others: AUTO — `get_eligible_students` drops the candidate so no `NotificationEvent` is ever created for them; MANUAL — `send_manual_notifications` skips them BEFORE the event is created (no orphan "sent" row), while an AUTO-only block does not stop a coach hand-picking them manually, and vice versa (a MANUAL-only block leaves AUTO eligibility untouched); ALL — `send_class_reminders` skips them (reported in `result["blocked"]` with name+reason) while an invitation-only block (auto+manual, not `all`) leaves reminders alone entirely, since a reminder is about a class the student is already enrolled in, not an invitation. The delivery choke point `_send_system_message` is the backstop: with `all` set, it refuses `notification_invite`/`notification_reminder`/`waiting_list_offer` (returns `None`) but still delivers `text` and `waiting_list_placed` (cancellation notices, "you got the spot") — unavailability blocks solicitations, never the coach-student channel — and an unblocked-for-`all` student (even with auto+manual set) still receives invites through the backstop. `student_notification_preferences.preference_blocked_players` reports `{playerId, name, reason, cause: "preference"}` — same shared `blocked`-array shape as PAD-107's `cause: "unavailable"` from `test_student_availability_blockers.py`, since both tickets feed one array on the notify routes. `PATCH /api/auth/me` tests (`user_service.update_own_profile_service`) pin the PAD-93 boolean trap directly: an explicit `False` must be WRITTEN, not swallowed as falsy/absent; updates are partial and each flag independent; `notif_block_reason` is trimmed and an empty string clears it to `None`; a non-boolean flag value raises `ProfileValidationError(status=400)` rather than being coerced; and the full round-trip through `GET`/`PATCH /api/auth/me` (camelCase `blockAutoInvitations`/`blockManualInvitations`/`blockAllNotifications`/`notificationBlockReason`). Finally, both coach-facing serializers (`player_service._serialize_coach_player_relation` — the roster list — and `Player.coach_player_info()` — the edit-sheet echo) must independently carry the same `notificationsBlocked`/per-flag/`notificationBlockReason` signal.
